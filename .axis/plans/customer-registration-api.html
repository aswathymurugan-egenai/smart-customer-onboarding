Key tradeoff · accepted by the user

Truthful status codes let the form show the exact problem at once. They also let anyone ask the API whether an email is registered. Rate limits and a bot check slow probing down and do not stop it, and phone numbers and tax IDs carry the same exposure.

Approach · three options from shaping

Who decides the outcome

Approach A won because the same input always gets the same status and every outcome can be tested offline.

A: rules decide, model advises B: the agent decides C: chat first
Who sets 201, 409, 422 Code and the BigQuery transaction The model, through tool calls The model, through conversation
Model failure Registration proceeds, no advice Registration fails or stalls Onboarding stops
Same input twice Same status Can differ Can differ
Offline testing Unit and API tests with fakes Model mocks for every outcome Scripted conversations
Contract Fixed operations, fixed outcomes Fixed operations, model-chosen outcomes No predictable contract

Designs set aside inside approach A

— Set aside

A bare MERGE for uniqueness. Insert-only MERGEs do not conflict, so two concurrent registrations of one email can both insert.

— Set aside

ADK BigQueryToolset. Its execute_sql runs SQL the model writes; custom tools call the same services as the REST routes.

— Set aside

Every model call through ADK. Typo and duplicate advice are one prompt each, so the advisor calls google-genai directly.

— Set aside

A Next.js proxy route. It would hide the client IP that rate limiting needs; direct calls use a CORS allow-list.

BigQuery behavior and the plan's response

Documented behavior What the plan does
An insert-only MERGE does not conflict with concurrent DML Opens every registration with DELETE … WHERE FALSE to take the table lock
A losing transaction aborts at once and is not queued; Google advises a 60-second wait Retries with jitter for up to 10 s, then 503 with Retry-After: 60
Primary keys are NOT ENFORCED The MERGE ON clause is the uniqueness rule; a check query detects breaches
Streamed rows cannot be changed by DML for 30 minutes Writes customers through DML query jobs only
Parameters cannot be NULL or name a table Sends empty strings with NULLIF; validates the dataset name from configuration

Contract · OpenAPI 3.1, committed and diffed in CI

Four operations

The brief's two endpoint lists merge into one contract. agent/onboard is dropped, because the assistant explains and the register route onboards.

Operation Statuses Returns
POST /api/v1/customers/register 201 409 422 403 429 503 Customer id and warnings; 409 names the matched fields only
POST /api/v1/customers/validate 200 422 429 The verdict per check and any typo suggestion; 422 only for a malformed body
POST /api/v1/customers/check-duplicate 200 403 422 429 Exact matches and the likely-duplicate warning; writes no customer
POST /api/v1/agent/chat 200 422 429 503 The reply, suggested actions, and registration status taken from the tool result
  • check_circleEvery error is RFC 9457 problem+json with a stable type URN.
  • check_circleThe 201 carries the id in its body and no Location header, because a public customer read endpoint would expose personal data.
  • check_circleA repeated Idempotency-Key replays the original 201; a new body under the same key gets 422.

Risks · one blocker, six major

Risks and mitigations

  • warning

    BlockerThe briefed Gemini 2.5 models are being retired.

    The Gemini API routes 2.5 requests to successors from 2026-12-01, and Vertex AI listed a 2026-10-20 retirement. Model ids are configuration, the platform check calls each one, and no status depends on a model.

  • warning

    MajorRegistrations serialize on the table lock.

    A losing transaction aborts at once. Jittered retries for 10 s, then 503 with Retry-After; a transactional store waits if conflicts pass 1%.

  • warning

    MajorA MERGE without the lock can insert one email twice.

    The lock statement opens every transaction, a test asserts its position, and the duplicate-keys check detects any breach.

  • warning

    MajorAnyone can probe which emails, phones, and tax IDs are registered.

    Accepted for email. Per-client limits, the bot check, and a client hash in the audit table make probing slower and visible.

  • warning

    MajorPersonal data reaches model providers.

    Prompts carry no tax ID or full phone, candidates go as opaque refs, and the OpenAI fallback is off by default.

  • warning

    MajorNext.js 15 security releases end on 2027-01-31.

    Pin the latest 15.x and settle the move to 16 before production.

  • warning

    MajorPrompt injection through chat or form fields.

    The register tool takes no model data, only the API grants confirmation, and outputs are schema-validated.

  • info

    MinorSeven smaller risks.

    Per-instance sessions and limits, tiny daily partitions, shared phone numbers, register latency, hash-key rotation, unverified ADK details, and a stale disposable list. Each has a mitigation in the plan.
